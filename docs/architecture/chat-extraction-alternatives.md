# Способы получить содержимое чата с агента: сравнение

Статус: исследование (2026-10-21), решений не принимает. Связано с `screen-parser.md` (как устроено сейчас)
и `docs/features/31-agent-feed.md`, `36-agent-feed-styles.md`, `16-host-service-analysis.md`.
Схемы: `diagrams/10-sources-map.png`, `diagrams/11-hybrid-target.png`.

Пометки: **[проверено]** — видел на этой машине (`--help`, живые снимки, код проекта);
**[по документации]** — известно из публичного описания продукта, здесь не проверялось: перед работой
проверить руками.

## 1. Что нужно от источника

Лента — это чат, поэтому от источника нужно:

1. **Полнота и точность**: настоящий Markdown, границы ходов, мышление, полные аргументы и результаты инструментов.
2. **Живость**: хвост беседы без задержки, вопросы и разрешения, спиннер, набранный текст.
3. **Работа с уже идущим сеансом**: пользователь запускает агента в tmux сам (на ноутбуке и с телефона),
   приложение подключается к нему, а не владеет им.
4. **Охват**: Claude Code и agy (и дальше Codex, Grok…) без отдельной инженерии под каждого.
5. **Устойчивость к обновлениям** агента: не ломаться при смене вёрстки.
6. **Цена и приватность**: батарея телефона, трафик, данные не уходят третьим лицам.

## 2. Варианты

### A. Текст экрана (`capture-pane -p -J`) — сейчас

Снимок панели, разбор вёрсткой (`screen-parser.md`). **[проверено]**

- Плюсы: работает с любым идущим сеансом без согласия агента; видит меню, спиннер, поле ввода, раскрытую
  историю; не требует установки на хост (кроме tmux).
- Минусы: стили потеряны, Markdown восстанавливается эвристиками, обрезанные результаты, перенос слов, хрупкость
  к смене вёрстки, полинг (удалённая команда каждые 3–10 с).

### B. Файл сессии (JSONL) — сейчас, как дополнение

Claude: `~/.claude/projects/<slug>/<id>.jsonl`; agy: `~/.gemini/antigravity-cli/brain/<id>/.system_generated/logs/transcript.jsonl`.
Приложение находит «свой» файл по процессу панели и по id сессии из хука (`~/.ssh-app/run/sessions`). **[проверено]**

- Плюсы: полный Markdown, мышление, полные аргументы/результаты, `isSidechain` (подагенты), стабильные поля;
  не зависит от вёрстки TUI.
- Минусы: запись отстаёт от экрана (нет живого хвоста), нет меню/спиннера/ввода; формат внутренний, не
  обещан; путь и выбор файла нужно угадывать (две сессии в одной папке); у agy структура иная.

### C. Экран со стилями (`capture-pane -e`)

Тот же снимок, но с SGR-последовательностями. **[проверено на живых панелях]**

- Claude: жирный `ESC[1m`, инлайн-код цветом `38;5;153`, список `- `, заголовки — жирные строки без `#`.
- agy: жирный `ESC[1m`, курсив `ESC[3m`, код `ESC[94m`, заголовки литералом `### …`, список `•`, код в блоках —
  256-цветная подсветка.
- Плюсы: возвращает разметку, потерянную в A (жирный, код, заголовки); дешёвое расширение A (тот же канал и
  скрипт, другая очистка); остаются меню/спиннер/ввод.
- Минусы: соответствие «стиль → разметка» зависит от темы терминала и версии агента (профиль на агента с
  запасным вариантом); вывод надо чистить уже после разбора стилей, поэтому `strip_ansi_codes` встаёт позже
  в конвейере; остальные минусы A сохраняются.

### D. Сырой поток панели + эмулятор терминала

`tmux pipe-pane -O` или control mode `tmux -C` (`%output`) отдаёт байты, которые агент пишет в панель; на хосте
или в ядре их ведёт эмулятор экрана (в Rust — `vt100`, `alacritty_terminal`, `termwiz`). **[tmux — по документации;
control mode уже упомянут в `16-host-service-analysis.md`]**

- Плюсы: настоящая модель экрана (ячейки со стилями, курсор, альтернативный буфер), события без полинга,
  нет проблемы «кадр в середине перерисовки», можно хранить историю дельт.
- Минусы: самый сложный путь (разбор потока, потеря байт при обрыве SSH — нужна переинициализация снимком,
  поддержка двух экранов tmux), эмулятор должен жить у сеанса (демон на хосте, а он у нас «только пока есть
  телефон» — `project_host_service_decisions`); выигрыш над C — в основном отсутствие полинга и тонкая
  синхронизация, а не новая информация.

### E. События хуков агента

Хуки (`SessionStart`, `PreToolUse`, `PermissionRequest`, `Stop`, `Notification`…) вызывают `ssh-app-host hook`;
он у нас уже пишет реестр сессий и очередь одобрений. **[проверено: реализовано, `agent_hooks`, `approval_queue`]**
Claude передаёт хукам JSON с `session_id`, `transcript_path`, именем инструмента и вводом **[по документации]**.

- Плюсы: мгновенные структурные события (разрешение, конец хода, уведомление), точное соответствие сеанс →
  файл, ничего не парсится с экрана; идеально для пушей и карточек.
- Минусы: события, а не содержимое чата (текст ответа в большинстве хуков не приходит); требует установленных
  хуков и согласия агента; набор событий разный у агентов.

### F. Headless-режим: приложение само запускает агента

Оба агента умеют не-интерактивный режим с потоковым JSON. **[проверено `--help`]**

- Claude Code: `claude -p --output-format stream-json [--include-partial-messages] [--input-format stream-json]`,
  `--resume <id>`, `--session-id`, фоновые сеансы `claude --bg`, `claude attach <id>`, `claude logs <id>`,
  `claude agents`.
- agy: `agy -p --output-format stream-json --input-format stream-json` (NDJSON-сообщение на ход),
  `--conversation <id>`, `--json-schema`; подкоманды `mcp`, `remote-control`.
- Плюсы: чистая структура (сообщения, вызовы, токены, частичные куски), никакой вёрстки; устойчиво к
  обновлениям; можно строить полноценный чат, а не зеркало терминала.
- Минусы: это **другой сеанс**, а не тот, что идёт в tmux: нельзя «подключиться» к уже запущенному TUI; теряется
  терминальный интерфейс агента (меню, `/`-команды, горячие клавиши) — их нужно воспроизводить; разрешения и
  интерактивность работают иначе (режимы разрешений, колбэки). Подходит как **отдельный режим вкладки**
  («чат-вкладка» без TUI), а не как замена ленты для идущего TUI.

### G. Официальный remote-control агента

Оба агента имеют удалённое управление сеансом через облако вендора: Claude — `--remote-control [name]`,
agy — `--remote-control` и демон `agy remote-control start|status|stop`. **[проверено `--help`; протокол и
условия не изучены]**

- Плюсы: вендорский канал к **идущему** сеансу, без парсинга.
- Минусы: данные идут через стороннее облако (противоречит принципу «ничего третьим лицам», `35-push-relay.md`
  и модели безопасности), протокол закрыт и не обещан третьим клиентам, привязка к аккаунту и тарифу.
  Для нашего продукта — только как справочный вариант.

### H. IDE-интеграция и MCP

`claude --ide` подключает агента к IDE по локальному каналу, `mcp` добавляет серверы инструментов.
**[`--ide` и `mcp` проверены в `--help`; устройство канала — по документации, не изучено]**

- Плюсы: официальный структурный канал, который IDE получает от агента.
- Минусы: канал локальный и закрытый (lock-файл, сокет), рассчитан на редактор; нет гарантии на сторонний
  клиент; приложение не IDE. Вариант на будущее после проверки протокола.

### I. Телеметрия и statusline

Claude умеет отдавать телеметрию (OpenTelemetry-события/метрики) **[по документации]**; statusline-скрипт
получает JSON с моделью, контекстом и лимитами **[проверено: уже используется для usage-полоски]**.

- Плюсы: структурные числа (контекст, токены, стоимость, модель) без парсинга экрана.
- Минусы: не содержимое чата. Как источник текста — не подходит; как источник статуса — хорош и уже в деле.

### K. MCP-сервер ssh-app для агента

Агент зовёт наши инструменты (`ask_phone`, `notify_phone`, `show_artifact`…). Чат не извлекает, а даёт агенту
структурный канал к телефону. **[изучено: `mcp-channel-study.md`; живой запуск не делался]**

- Плюсы: структурные вопросы и уведомления без разбора экрана; карточки и прогресс как данные.
- Минусы: агент вызывает инструмент по своей воле (хуки это гарантируют, MCP нет); недоверенный ввод; два формата
  регистрации; `--permission-prompt-tool` работает только в `--print`, наши хуки он не заменяет.
- Решение (2026-10-21): **не делаем**. Живая проверка прошла (Claude вызывает инструмент, 25 с ожидания работает),
  но выигрыш небольшой: обязательность вызова всё равно держится на хуках, а структурные вопросы уже закрыты экраном.

### J. Консоль без tmux (PTY владеет приложение)

Приложение запускает агента в своём PTY на хосте и сохраняет поток. Отвергается: ломает базовую модель
«сеанс живёт в tmux, телефон лишь подключается» (`AGENTS.md`, пункты 1 и 3).

## 4. Рекомендация

Слои с запасными путями (`diagrams/11-hybrid-target.png`):

1. **Основа истории — файл сессии (B).** Он даёт точный Markdown и всё, что экран режет. Уже есть.
2. **Живой хвост — экран со стилями (C).** Один шаг от нынешнего A: захват с `-e`, разбор SGR в Markdown по
   профилю агента (Claude: жирный → `**`, цвет 153 → инлайн-код; agy: жирный, курсив, цвет кода), запасной
   вариант — текущий текстовый разбор. Закрывает жалобу «парсер теряет Markdown и цвета».
3. **Мгновенные события — хуки (E)** для карточек, одобрений и пушей (уже есть) и для точного соответствия
   сеанс → файл.
4. **Запасной путь** — экран без стилей (A) и «Terminal output».
5. **Статус** — statusline (I).

Отложить и проверить отдельно: D (если полинг и «кадр в середине перерисовки» останутся проблемой после C),
F (отдельный режим «чат-вкладка» без TUI — для Ollama он уже фактически такой), H (после изучения протокола).
G не использовать (облако вендора).

## 6. Риски

- Цвета и жирность зависят от темы и версии агента: профиль обязан иметь запасной вариант (текстовый разбор) и
  не должен ломать вывод при незнакомом цвете.
- Всё, что идёт с экрана — недоверенный текст: разбор SGR не должен пропускать сырые последовательности в ленту.
- Форматы файлов сессий внутренние; нужен тест-страж на настоящих фрагментах и мягкая деградация.
