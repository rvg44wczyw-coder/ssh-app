# Security findings: feature 32 T2, helper `ls` and the path policy (2026-10-19)

## 1. Scope

Commit `4120e6e` on `main` (clean tree). Reviewed: `crates/host/src/files.rs` (`dir_policy`,
`file_policy`, `entry`, `list`), `crates/host/src/main.rs` (`ls_reply`),
`crates/core/src/file_browser.rs` (`build_helper_ls_command`, `parse_helper_listing`,
`is_restricted`), `crates/core/src/host_api.rs` (`list_remote_directory` helper path and fallback,
and, for the "is `restricted` the only guard" question, `read_remote_file_preview`).

Applies: file-system access driven by untrusted input (path argument, names and links created by
any local account or by a checked-out repository), subprocess (`tmux`), parsing of a host reply,
resource exhaustion. Ruled out: crypto, replay, downgrade, key confusion, timing (no secrets are
compared); writes (the helper writes nothing).

Live tests (own local subprocesses, helper binary from the tree, temp tree in the scratchpad with a
fake `HOME` containing `.ssh`, `.aws`, `Library/Keychains`): link chains (absolute, relative,
link-to-link, link to a key file, loops), case variants (`.SSH`, `.AWS` on case-insensitive APFS),
`/.` and `/..` forms, FIFO and Unix-socket entries, names with ESC, newline and U+202E, a
directory named with U+202E, argument abuse (`--path` values `--hidden`, `-x`, `$(id)`, `'; id; '`,
empty; `--pane` values `-x`, `a;b`, `../x`, 70 characters, empty; unknown flags; missing values),
60 000 dotfiles + 100 files, 20 000 symlinks. Code analysis only: the `$1` quoting in the core
script, hostile helper replies (covered by the core unit tests), the canonicalize/read race, hung
network mounts.

One honest note on isolation: my first `--pane -x` run inherited `$TMUX` and so asked the
developer's real tmux server (a read-only `display-message`). Afterwards `tmux display -p
'#{pid}'` was still 35350 and `show-environment -g HOME` still `/Users/dev`; every later tmux run
used `env -u TMUX TMUX_TMPDIR=<private dir>`.

## 2. Findings

### 1. [InputValidation] Low: bidi / zero-width characters stay in `path`, `parent_path` and the header path

Where: `crates/core/src/file_browser.rs` `parse_helper_listing` (`current_path` only rejects control
characters; only `name` goes through `display_safe`), `FileBrowserSheetView` (`Text(listing.currentPath)`).

Scenario: a repository or another account creates a folder named `dir<U+202E>evil`. Listing it
returns `path` ending in `dir‮evil` (verified live) and the header path bar shows it reordered
(spoofing which folder `cd Here` and `Insert Path` will use). The entry names are marked correctly,
the path is not.

Fix direction: show paths through `display_safe` (keep the raw string for navigation), or add a
separate display field; the helper could also refuse to canonicalise into such a path.

### 2. [InputValidation] Low: a session name starting with `-` (or a prefix of another name) lists another session's folder

Where: `crates/host/src/files.rs` `valid_session_name` / `pane_path` (`tmux display-message -p -t
<name>`); same alphabet in the core's `validate_session_name`.

Scenario: tmux accepts `-x` as a target and resolves it to the current pane. Verified: `tmux
display-message -p -t -x '#{pane_current_path}'` exits 0 and prints another pane's directory; the
helper's `ls --pane -x` returned that directory. tmux also matches targets by prefix / pattern when
the exact name does not exist, so a tab named `ab` can show the folder of session `abc`. The shell
version had the same behaviour; the user only sees the wrong folder of their own sessions.

Fix direction: target `=<name>` (exact match) and refuse names starting with `-` in both validators.

### 3. [DoS] Low: a flood of hidden entries pushes ordinary files out of the listing, and the app drops the `truncated` flag

Where: `files.rs` `list` (`READ_LIMIT` counts every directory entry, including the dotfiles that are
skipped when `--hidden` is off), `RemoteDirectoryListing` (no truncated field).

Scenario: a folder with 60 000 dotfiles and 100 normal files, listed with hidden files off, returned
42 entries and `truncated: true`; the other 58 files were never read. The app shows no notice, so a
repository can hide files from the browser. Cost was small (0.0 s wall, 3.8 MB RSS), so this is a
display-integrity problem, not resource exhaustion.

Fix direction: skip hidden entries before they count toward the read limit, expose `truncated` to
the UI ("more entries not shown").

### 4. [DoS] Low (code analysis): no time budget in `ls`; a symlink into a hung mount blocks until the 20 s watchdog

Where: `files.rs` `entry` (`std::fs::canonicalize` per symlink, `real.is_dir()`).

Scenario: a folder with symlinks whose targets sit on a stalled NFS / SMB / autofs mount makes
`canonicalize` block; the helper is killed by the login-shell watchdog after 20 s with no output, the
app falls back to `ls -la` (which does not touch targets) and succeeds. Effect: a 20 s delay per
listing, not a lasting failure. Measured without a hung mount: 20 000 symlinks = 1 s. The hung-mount
case itself was not reproduced (no safe way to build one locally).

Fix direction: a deadline for the whole listing (resolve links from a worker thread and give up
after a few seconds, then mark the remaining links `restricted: false, target_kind: unknown` or
resolve at most N links).

### 5. [PathTraversal] Informational: canonicalize-then-`read_dir` is not atomic

Where: `files.rs` `list` (`canonicalize` → string → `read_dir(&real)`).

If a path component is swapped for a link to `.ssh` between the two calls, the names, sizes and
modes of `.ssh` entries are listed (never contents; reading goes through the core's separate
validated read path). It takes an actor who can change a component of a folder the user is listing:
the same account, or another account inside a world-writable folder such as `/tmp`. Fix direction:
open the directory once (`O_DIRECTORY | O_NOFOLLOW` on the canonical path), re-check the policy on
the descriptor's path (`F_GETPATH` on macOS), list from the descriptor.

### 6. [Informational] Silent fallback to `$HOME`

A requested folder that is missing, not a directory, or a broken link makes the helper list `$HOME`
and answer `ok: true` with `path` set to the home folder (verified with a broken link). This copies
the old shell behaviour and is not a leak (the user's own home), but the app does not say that the
request was replaced. A reply flag (`"fallback": true`) would let the UI tell.

### 7. [Informational] Policy scope

- The rules are textual, on the canonical path, so a **hard link** to a key file named innocently
  (`ln ~/.ssh/id_ed25519 ~/work/notes.txt`) is neither restricted nor refused by the read path; only
  the account owner can create it.
- The deny list is a copy of the pre-existing one: it has no entry for other common secret stores
  (`~/.config/gcloud`, `~/.config/gh`, `~/.docker/config.json`, `~/.password-store`, application
  token stores). Extending the shared table (`crates/host/testdata/fs_policy_cases.tsv`) updates the
  helper and the core together.

## 3. Checked and held

- Policy through links (live): absolute link, relative link (`../home/.ssh`), link-to-link, link to a
  key file, link to `Library`: `ls` of the link is refused (`/.ssh` restricted) and the link entries
  carry `restricted: true` (`l_abs`, `l_chain`, `l_rel`, `l_key`, `l_key2`); `Library/Keychains` is
  flagged inside `Library`; a link loop terminates.
- Case and path forms (live, case-insensitive APFS): `.SSH`, `.AWS`, `…/.ssh/.`, `…/w/../home/.ssh`
  and `…/.ssh/..` (which is just the parent) all behave correctly: the first four are refused, the
  last lists the parent.
- Entries: FIFO and socket entries are listed as `other` (the core skips them) and nothing opens
  them; names with ESC or newline are not listed (live); non-UTF-8 names cannot be created on APFS
  (kernel rejects them) and the code skips them; bidi names are marked in `name`.
- Arguments: `--path` values `--hidden`, `-x`, `$(id)`, `'; id; '` are treated as plain paths
  (fell back to the home listing), empty is refused, unknown flags and missing values give usage
  errors, `--pane` rejects anything outside `[A-Za-z0-9_.-]{1,64}`.
- Core: the path travels as `"$1"` through `shell_quote` (unit test checks the script and the
  absence of the path in it); hostile reply handling is covered by tests (names with `/`, `..`,
  controls and `other` kinds dropped, 2000 entries cap, `current_path` with ESC → fallback, `ok:true`
  without entries → fallback, `ok:false` shown as an error).
- Is `restricted` the only guard? No: `read_remote_file_preview` still validates the requested path
  (`host_api.rs:1116`) and the resolved path (`:1130`) on its own; the lock in the browser is a
  convenience on top.
- Resources: 60 000-entry folder 3.8 MB RSS, 20 000 links 1 s; at most 2000 entries leave the helper
  and the core re-caps at 2000.

## 4. Verdict

Findings (highest severity: Low): no Critical/High; four Low items and three informational notes.
None blocks T2; findings 1–3 are cheap and should be fixed before T3 (they touch what the user sees
as the folder and its contents).

## 5. Resolution (2026-10-19, same day)

- 1: the header path goes through the new exported `display_safe_text` (the raw string is still
  used for navigation); test `display_safe_text_marks_bidi_and_pane_target_is_exact`.
- 2: tmux targets are `=<name>` in the helper and in the shell listing; names starting with `-`
  are refused by the helper and by `validate_session_name`. Tests: same core test,
  `dotfile_flood_does_not_hide_ordinary_files_and_pane_names_are_strict`.
- 3: skipped entries no longer count toward the read limit; `RemoteDirectoryListing.is_truncated`
  is filled from the helper and the browser shows "More entries exist than are shown". Test:
  the helper flood test above (2500 dotfiles + 20 files, hidden off: all 20 files).
- 4: `ls` runs in a worker thread and answers `{"error":"timeout"}` (no `ok`) after 8 s, which the
  core treats as "no usable reply" and falls back to the plain listing. Not reproduced against a
  real hung mount.
- 5, 6, 7 stay as documented (informational; 5 is the candidate for T3's descriptor-based open).

Verdict after fixes: clean for T2.
